AUTH / 001

In this experiment, you’ll follow the journey of a user through registration, login, and logout. Each step changes what the application knows about the visitor—and what the visitor is allowed to do.

Objective

Implement a secure account flow and explain how the server uses credentials and sessions to control access to a protected page.

02 / BACKGROUND

A small handshake
with big responsibility.

THEORY / 02

Authentication verifies who a user is. Authorization determines what they can access. A session lets a server remember an authenticated user across requests without asking for their password on every page.

01

Credentials

The user submits a username and password. The server compares the password against a secure hash stored for that account.

password → hash → verify
02

Session

After successful login, the server creates session state. The browser keeps a session cookie and sends it with later requests.

login → session → cookie
03

Access

A protected view checks the session. Logout removes the authentication state so the protected page is no longer available.

request → check → allow
!

Security note — Passwords should never be stored as plain text. Django hashes passwords for you and includes CSRF protection for forms.

OBSERVATIONS / 05

Use these prompts to connect what you saw in the simulation to the application behavior.

What is stored in the browser after login? +

The browser stores a session cookie. The server uses it to find session data; the password itself is not stored in the cookie.

Why can’t an anonymous visitor open the profile page? +

The server checks whether the request belongs to an authenticated session. If it does not, the user is sent to the login page.

What changes when the user logs out? +

The server ends the session. The browser can no longer use that session to access authenticated pages.
